# Adversarial implementation review: observer commit 9ccebb5 (`pr.tape` hourly capture of production's /tape)

**Disclosure.** I am an instance of the same model family as the author (Claude Fable 5.1), briefed by the author. My independence is limited to not having written the code: I read the diff and the surrounding code, ran the suites, and measured against the real tape and the server's /tape handler; I did not call any remote host.

**Suites (package dir, Node 22.23.4):** unit 59/59 passed, durability 14/14 passed, math 2544/2544 agree. Helpers: `round6/review_tmp/measure.js`, `review_tmp/simulate.js` (drives the real `pinradarSource.tape` task against a fake server that applies production's exact filter and order from `base_I2_pinradar_server.js:5166-5169`, fed with the real 10 MB tape).

## Facts the change rests on (verified)
* Server: samples `t > since` then rows `ts > since`, emitted as one block of `s` lines followed by one block of `d` lines (not interleaved); ring of `TAPE_MAX` = 3000 `d` rows; samples kept from `rows[0].ts − 960 s`. A `d` row is written **once per second only inside the LOCKED horizon (tau ≤ 300 s)** (`server:4114`), i.e. the final 300 s of each 15-min window. `boot` rows go only to `TAPE_FILE` (`server:3968`), never into the ring that /tape serves.
* Real tape: 3,000 `d` rows over 8,399 s with exactly 9 holes of 601 s (one per window gap) and 2,990 consecutive deltas ≤ 1.5 s; 9,675 `s` rows at 1 Hz with 0 holes; 0 `boot` rows; `d` row ≈ 3,224 B, `s` row ≈ 50 B. `JSON.stringify(JSON.parse(line)) === line` for 12,675/12,675 lines, so `rows` is stored byte-faithfully, in published order.

## Findings
1. **Material — the `gap` detector fires on two thirds of normal pulls** (`sources.js:141`, `TAPE_GAP_MS` at `:28`). The cursor is the newest `d` ts, and `d` rows stop for 600 s after every window close, so unless the pull lands inside a window's final 300 s the first new row is ~601 s after the cursor. Simulation at 30 phases of the 15-min cycle: the second hourly pull records `gap:{ms:601000}` in 20/30 phases; with the hourly cadence (3600 = 4 × 900) the same phase repeats, so a deployment either records a false gap every hour or never. A real loss (production restart inside the hour, two failed pulls) is then indistinguishable from the by-design hole except by size. Nothing is merged silently (good), but the field is noise. Fix: detect holes from the 1 Hz samples (continuous by construction: 0 holes in 9,675) against the previous pull's last sample `t`, and/or compute consecutive-`d` holes on the full reply with the ticker on each side (as `orderBreaks` does for predictions, `:47`), rather than first-row-minus-cursor.
2. **Material — samples are stored twice, unflagged** (`:134-142`). The cursor is a decision ts, but production filters samples by `t > since`, so every sample between the newest `d` row and the pull time is returned again next hour. Simulation: 0–571 duplicates per hourly pull (mean 192, ≈5 % of an hour's samples), counted in `received`/`samples`. No sample is lost (samples with `t ≤ D` are pushed to the ring before row `D` is recorded, `server:4067/4098`; only a production clock step could reorder). Fix: keep `lastSampleT` in state and drop `s` rows with `t ≤ lastSampleT`, or document that consumers must dedupe `s` by `t` and `d` by `ts`.
3. **Material — a failed pull is retried only after an hour** (`:149` sets `due` before `run`; `:143`). The ring holds 2.5 h, so one failure is tolerated, two consecutive failures lose ≈30 min of rows, three lose ≈1.5 h, with no sooner attempt. The predictions catch-up already uses a 5-min backoff (`:92`); the same here (`if (!r.ok) S.due.tape = now() + 300e3`) would survive ~1.4 h of continuous failure instead of 1 h and recover transient failures in minutes.
4. **Material — `tapeTs` is restored without the plausibility check every other cursor gets** (`observer.js:134` carries `saved.pinradar` through; `:137-139` sanitise `predTs`/`ledgerSeq`/`sigTs` with `≤ now + 864e5`; the task only checks `okInt`, `sources.js:133`). A future-dated `tapeTs` in a damaged `state.json` makes production return nothing, `newest` stays `= since`, and the task stores `ok` records with 0 rows forever. `tapeTs` is persisted (`:186`, `{ ...pr.state }`) and restored; a lost state file resets it to 0 and re-pulls the whole ring (≤ 2.5 h of duplicate rows, unflagged; same dedupe need as 2).
5. **Material — no operator-visible failure signal.** A failed pull is a `pr.tape` record with `status`/`error` inside the encrypted raw stream only. `status.json` (`observer.js:187`) and `obs.heartbeat` (`:214`: `predCursor`, `ledgerSeq`) carry no tape cursor; `errors` counts thrown exceptions, not HTTP failures; the window log has no `pr.tape` case (`windowlog.js:51-74`); `derive`/`report` have no consumer. Only the owner, decrypting on their machine, would notice. Fix: add `tapeTs` and the last tape status to the heartbeat/status, and a log line on failure.
6. **Material — the data dictionary describes a mechanism that cannot occur** (`DATA_DICTIONARY.md:22`, comment `sources.js:127-131`): "one `d` row per second" (true only in the final 300 s of each window), "`boot` markers" (never served by /tape; `boots` is always 0, so the restart-detection story for the tape is dead), and no mention of 2 or 1. Restart detection exists only via `pr.restart` (health uptime, `:68-72`); a consumer must join by time. Also a production clock step back moves `predTs` (`:64`) but not `tapeTs`, so rows written after a backward step are filtered out by `ts > since` until the clock passes the cursor (minor, but the mechanism was not extended).
7. **Minor — resource use on the observer (measured on the 10 MB real tape).** `ndjson` parse 128 ms (heap +22 MB); `store.encrypt` of the record 196 ms (stringify 118 + deflate 103 + AES/base64); an hourly pull (3.82 MB plain, 5,119 rows) is roughly 40 % of that. Both run on the single thread, so the Kalshi book lane (1 Hz in the final 300 s) can be delayed ≈0.3 s once at start and ≈0.15 s hourly: inside its cadence, no `obs.stall` (5 s). The network wait (≤ 8 s timeout, `http.js:17`) blocks only the pinradar lane (predictions ≤ 8 s late, inside its 120 s overlap). Transient memory ≈ 60 MB (text + objects + stringify) on a 512 MB Starter: fine. `maxBytes` 32 MB gives 3× margin at `TAPE_MAX` 3000; if production raised `TAPE_MAX` above ≈ 9,900 every reply would be cut, `ok:false`, and the cursor could never advance (/tape has no pagination). The 8 s timeout needs ≥ 10 Mbps for the first (full-ring) pull; same-region Render should manage, but a timeout also retries hourly with `since=0` forever. Production-side cost not in the README's "6 small GETs a minute": the handler stringifies the reply synchronously on production's event loop, ≈120 ms for the first pull and ≈45 ms hourly (`server:5169`).
8. **Minor — store growth.** Deflate ratio 0.081 at the store's level (zlib default): one hourly record → 0.30 MB deflated → 0.40 MB base64 line → **≈ 9.7 MB/day (~290 MB/month)**, plus 1.05 MB once for the first pull. Against 1,072 MB in 16 days (67 MB/day) that is +14 %; the 10 GB disk lasts ≈ 116 days from today instead of ≈ 133 (the host warns at 80 %). Cost downstream: `derive` decrypts every record in each of its two passes (`observer.js:337`, kind is inside the ciphertext): ≈ 100 ms and ≈ 40 MB transient heap per full-ring record (≈ 40 ms / 16 MB hourly), ≈ 1 min per month of data; durability F3's "96 MB heap" result was not re-run with `pr.tape` records present.
9. **Minor — security: no widening.** `/^\/tape$/` is anchored (`http.js:12`); the query string is not part of `pathname`; `since` is `okInt`-checked before interpolation; GET-only, redirect refusal, HTTPS, the 32 MB cut and the no-credential client are unchanged; Test 8 now rejects `/tape/x` and `/tapes`. The endpoint publishes production's top-20 book and decision internals, stored encrypted to the owner's key like everything else.
10. **Minor — tests do not exercise production's semantics** (`unit_test.js:418-433`). The fake server returns rows at `since+1000/+2000`: no samples-then-rows order, no 601 s inter-window hole (would have exposed finding 1), no duplicate samples (2), no cut/oversized reply, no timeout, no `tapeTs` round trip through `observer.js run`/`state.json` (4), `boots` asserted on a counter that can never be non-zero, "stored as published" asserted only as `rows.length === 3`. The e2e fixture server has no `/tape` route, so the e2e observer records a 404 hourly, unasserted. `ndjson` drops unparseable lines silently, so `received` is parsed lines, not published lines (minor fidelity note).

**Working-tree note (not in 9ccebb5).** While this review was written, `lib/sources.js` gained an uncommitted 2-line follow-up after `:142`: one `console.log('[tape] ok|FAILED … GAP … ms …')` per pull. It gives the host log a plain-text status (part of finding 5; `status.json`/heartbeat still carry no cursor) and, until finding 1 is fixed, will print `GAP 601000 ms` every hour at two thirds of deployment phases, and `boots=0` always. Left as found; it needs a test and a commit.

## Verdict: deployable with named fixes
Nothing here corrupts the store, weakens the read-only guarantee or loses rows in normal operation: the rows are stored byte-faithfully in published order and the cursor never skips a decision row. I would not deploy before fixing 1 (gap detector on samples or on consecutive rows), 2 (sample dedupe or documented), 3 (5-min retry after failure), 4 (`tapeTs` plausibility check), 5 (cursor and last status in heartbeat/status/log) and 6 (dictionary corrected: window-only rows, no boot markers, duplicates), with a unit test built on the server's real order, filter and 601 s holes (a slice of the real tape makes a good fixture) and durability F3 re-run with `pr.tape` records. Items 7–9 are acceptable as they stand and should be written down (store +14 %, production's ≈45–120 ms hourly stringify, the `TAPE_MAX` ceiling of ≈ 9,900 rows under the 32 MB cut).
