# Pre-registration: comparable historical cohort by volatility-reading scale (written before the run; 2026-11-16)
Observation motivating it: on the 202 common windows of Nov 12-15 the replay engine's raw volatility reading is 1.16-1.19 x the live engine's (round4/replay_live/compare.txt), so at equal geometry the replay crosses the LOCKED thresholds later and makes fewer early entries. The replay's [90,120]-s cohort is therefore selected on a stricter effective threshold than the live cohort.
Hypothesis H_comp: the live engine's [90,120] cohort is not comparable to the replay's because the live sigma is lower; a replay with its sigma scaled down to the live level admits more and earlier [90,120] entries, and THEIR historical loss rate is materially higher than 0 in 7,281.
Computation (fixed before running): replay engine (live I2 file, identical decisions to engine P) on the original Binance BTCUSDC data and real Kalshi settlements, Sep 1 - Nov 12 2026 (TEST period), one change: LIVE_VOL_SCALE = 1.03 / 1.19 = 0.866 (env; production uses 1.03). Outputs: exact-rule entries by seconds-left bin, losses, and the [90,120] count and loss rate; compared with the unscaled run of the same period (features_R_exact: Sep 1 onward [90,120] = 1,638 entries, 0 lost; 1,791 / 1 under the displayed rule).
Predictions: if H_comp explains the discrepancy, the scaled cohort shows a [90,120] loss rate of the order of the live 0.5 % (>= 3 losses in roughly 2,000 entries); if the scaled cohort still shows 0-1 losses, the sigma-scale difference does not explain it and the discrepancy survives this adjustment. This is an analysis of comparability, not a candidate rule; nothing from it is proposed for production.

Addendum (2026-11-16 08:19 UTC, after the Sep-Nov result, before the full-year run): the Sep 1 - Nov 12 scaled cohort gave [90,120] = 2,165 entries, 3 losses (0.139 %, upper95 0.358 %) against 1,638 / 0 unscaled on the same windows. The full year is now run with the same single change to estimate the comparable historical rate for the whole of 2026; the same bins and rules are read; no other variation is tried.

Robustness check stated before running (2026-11-16 08:27 UTC by the clock): a second way to build the comparable cohort is threshold-equivalence instead of sigma scaling: row by row the replay's pf reads 1.56 x the live pf at [90,120] (round5/transfer/rowcompare.txt), so a live reading of 0.2 % corresponds to a replay reading of about 0.31 %. The UNSCALED Sep 1 - Nov 12 traces are therefore read with the entry rule pf <= 0.0031 (first LOCKED/PROVEN row, 0 < tau <= 120). Prediction: if the sigma-scaled result is robust, this cohort shows a similar [90,120] count (about 2,000-2,400 entries) and a similar number of losses (2-4); a very different answer would mean the comparability adjustment is method-dependent and must be reported as uncertain. No further variants will be tried.

Addendum 2 (2026-11-16 17:3x UTC, stated before running): the measurement review of round 6 (round6/feed/review_measurement.md) finds that on the fit-period seconds the Binance proxy's 1-s RMS is 1.25 x the rebuilt fit-type index's (0.986 / 0.787, n = 31,904), not the 1.17-1.19 measured against BRTI and the live composite that the 0.866 scaling was built from. The scaling that puts the replay proxy at the fit-type scale is therefore 1.03 / 1.25 = 0.82 (the server clamps LIVE_VOL_SCALE at 0.8 minimum). One further run, Sep 1 - Nov 12, LIVE_VOL_SCALE 0.82, same pipeline and bins. Prediction: more [90,120] entries than the 0.866 run (2,165) and a loss count at least as large (3); if the loss rate rises materially above 0.14 %, the discriminator's H0 rate (0.14 %) was too low and must be revised to the measured comparable rate before any look (no data beyond the 12 entries / 0 losses counted at the 12:31 reading have been examined). No other scale will be tried.
