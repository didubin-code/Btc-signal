## 5. Event-driven vs polled, and what is achievable
- Pushed: Coinbase/Kraken/Bitstamp WebSockets (connectVenue l.869–893, reconnect backoff 500 ms→20 s l.894–901; quotes stamp lastQuoteTs and feed computeIndex). One Kalshi WebSocket (startKalshiWs l.2130–2150) carries ticker_v2 + orderbook_delta + trade for the market (l.2192–2196) and cfbenchmarks_value for BRTI (l.3080–3091; handler l.3094–3160); only ticker_v2 (→ yesBid/yesAsk and KAL.ts, l.2175–2181) and BRTI are used — orderbook_delta/trade are parsed and dropped (health kalshi.wsMsgs 137 M ≈ 764 msg/s).
- Polled: Kalshi market record REST every KALSHI_POLL_MS 1,000, KALSHI_POLL_FAST_MS 250 when τ ≤ KALSHI_FAST_TAU_SEC 120 (l.301–303, 1937–1946, non-overlapping l.1858); order book REST re-read when older than BOOK_FAST_MS 400 inside BOOK_FAST_TAU 300 s, else 1,500 (l.1319–1320, 1903–1914) — the book never comes from WS deltas, hence book age p50 308 ms inside 120 s and 546 ms before; 1 Hz index sampler (l.988–992); REST venue fallback 1,500 ms only when no venue is fresh (l.324, 2291–2313; never active); settlement poll 2,000 ms (l.405). Decisions: bgTick every 500 ms (l.4254–4276) mutates the sticky/reversal state and writes tape/ledger; `/radar` (l.4337–4466) recomputes computeLockSnapshot per request from live inputs with mutate:false (l.4454) — it is not served from a per-tick cache (confirmed by the incident: the page saw HIGH CONFIDENCE 22 ms before the tick). Page: loopPoll with pollGap 250/120 ms (repo l.669–677; served l.1027–1035 via a Worker clock), inFlight guard l.395, 8 s request timeout l.400, error backoff 1→8 s l.409–416, BACKEND LAGGING/NO DATA after 6/15 s silence (l.225, 529–540); local 150 ms index / 140 ms strip refresh from the browser's own exchange sockets (l.360, 678).
- Decision latency after a source tick today: from receipt (localTs or lastQuoteTs) to the next tick 0–500 ms (mean 250; <1 ms compute); worst seen ≈1,000 ms only through 1 Hz tape sampling, no stall >0.5 s found. Display: ≤250 ms poll wait + rtt 157–179 (p95 184–228, max 1,046) + ~8 ms render ≈ 300 ms typical, ≈1.8 s worst from observed components; measured 77 ms decision→served once. Before all that, the official print is 92 ms (p50) / 223 ms (p99) / 1.7 s (max) behind its source second and was 0.2–1.3 s late in both adverse moves, which our software cannot change.
- Achievable requirement, supported by the numbers above: **every exchange quote and official print is reflected in a decision within 600 ms of its receipt (p99)** (today ≤500 ms tick + ≤1 ms compute) **and shown on the page within 500 ms of that decision (p95)** (today ≤250 ms wait + rtt p95 184–228 + 8 ms ≈ 450–490 ms); the official-print source→receipt leg stays ≈0.1 s p50 / 0.22 s p99 with rare seconds-long gaps. To go tighter (decision ≤100 ms after receipt, display ≤250 ms) would require, without implementing anything here: computing the snapshot on message arrival (from brtiHandle27 / the venue onMsg) instead of the 500 ms timer; pushing decisions to the browser (SSE/WebSocket) instead of a poll that the inFlight guard caps at ~4 Hz (the 120 ms setting buys nothing at 170 ms rtt); giving BRTI its own Kalshi connection or dropping the unused orderbook_delta/trade subscriptions (the BRTI lag coincided with the moves); counting WS resubscribes and BRTI gaps in /health (seqGaps hides them); and posting client latency from whatever page is live (only the 2.8 page does, and no page has polled since Nov 14 ~01:30).
